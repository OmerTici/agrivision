AgriVision — Architecture, Security & Test Review

Combined staff-level review · iOS app + FastAPI embedder + Supabase · evidence-cited, read-only
branch ios-recognition 2 High 1 High (pending verify) 3 Med 4 Low AuthN solid SQL parameterized
One-line verdict. The core security primitives are genuinely well-built — JWT verification is correct (asymmetric-only, audience-pinned, alg-confusion-tested), all SQL is parameterized, and tenant isolation is enforced server-side. The real exposure is operational: an expensive CPU inference endpoint reachable by any self-registered user with no rate limiting, no upload-size cap, and no batch-size cap (cost-amplification DoS), plus a write path (animals insert) that depends entirely on RLS being correctly applied in the live project — which must be verified out-of-band.

Scope: server/app/*, server/sql/schema.sql, server/Dockerfile, download_models.py, scripts/setup_supabase.py, server/tests/*, AgriVision/Services/*, Config/AppConfig.swift, Info.plist. Every claim cites file:line. Items not confirmable from code (live RLS, Storage policy, Cloud Run ingress) are listed in §6.

Trust boundaries

  • AuthN enforced at current_uid (main.py:66,87) → verify_jwt (auth.py:23-35). /health has no auth (main.py:57-58).
  • Tenant isolation enforced server-side: MATCH_SQL … WHERE e.owner=$2 (db.py:46) and ANIMAL_OWNED_SQL … WHERE id=$1 AND owner=$2 (db.py:56), with owner always = the JWT sub.
  • The one client-trusted boundary: AnimalRepository writes animals.owner from a client-supplied value (AnimalRepository.swift:42-54), gated only by RLS WITH CHECK (owner = auth.uid()) (schema.sql:36) — runtime-dependent.

Data model

animals(id, owner→auth.users, name/tag/breed/sex/birth_date/status, created_at) and embeddings(id, animal_id→animals ON DELETE CASCADE, owner, vec vector(2152), image_path, created_at) (schema.sql:4-19). Owner scoping = owner on both tables + btree indexes (schema.sql:26-27) + RLS (schema.sql:31-39). No ANN index — exact scan by design (HNSW caps at 2000 dims; MiewID is 2152) (schema.sql:21-24).

JWT lifecycle. Minted by Supabase Auth (ES256, asymmetric — no HS256 secret, auth.py:1-3). Client reads it from the live SDK session per request: tokenProvider: { try? await SupabaseClientProvider.shared.auth.session.accessToken } (AgriVisionApp.swift:15) — always-fresh, SDK auto-refreshes. Server verifies via JWKS with algorithms=["ES256","RS256"], audience="authenticated" (auth.py:27-29), returns sub as uid.

Coupling / versioning risks

  • isIdentified = decision == "identified" (RecognitionModels.swift:32) — renaming the server's decision value silently flips identifications to false.
  • Non-optional score/margin: Double (RecognitionModels.swift:19-20) — if the server omits either, the whole response fails to decode.
  • Field/path string literals are hard-coded client-side — any server rename breaks silently.
  • Good decoupling: embedding dim (2152) and thresholds (0.60/0.05) are server-only (miewid.py:13 · config.py:16-17) — not referenced in the client.

03Security Risk Register

#TitleSevFile:lineAttack scenarioFix
1No rate limiting / cost-amplification on auth'd ML endpoints HIGHmain.py:65-110 Self-signup yields a valid JWT; attacker floods /identify//enroll. Each call runs a CPU MiewID pass on a scale-to-zero 1-worker container (Dockerfile:29) → spins instances, drives GCP bill, starves users. AuthN doesn't stop a valid token. Per-uid token-bucket limiter, Cloud Run --max-instances/concurrency caps, per-user daily quotas.
2No upload size cap + unbounded enroll batch HIGHmain.py:67,85,91-95 One /enroll with hundreds of large images is fully read into memory and stacked into one tensor (miewid.py:54) → OOM/CPU exhaustion; multi-hundred-MB body buffered with no limit. Decode precedes any size check. Max body size (proxy client_max_body_size / check content-length), cap len(images) ≤ 10 and per-file bytes before read(), reject 413.
3Decompression bomb: no Image.MAX_IMAGE_PIXELS override MEDmain.py:35-42 A tiny JPEG decoding to tens of MP allocates hundreds of MB on .convert("RGB"). PIL's default ~89 MP guard gives partial cover (caught as 422), but a sub-limit image still balloons memory. Image.MAX_IMAGE_PIXELS = 24_000_000 at import; validate img.size before convert.
4animals write trusts client-supplied owner, gated only by RLS HIGH
pending verify		AnimalRepository.swift:42-54,58-64
schema.sql:35-36		 iOS inserts animals.owner=<client value> over PostgREST. If RLS isn't applied/enabled (or differs from schema.sql), a user can create rows owned by another uid or read others'. Not re-checked server-side — 100% RLS-dependent. Verify RLS live (§6). Defense-in-depth: drop the client owner field; set via DB DEFAULT auth.uid() or BEFORE-INSERT trigger.

✓ What is genuinely solid (verified, not assumed)

  • JWT verification is correct. Asymmetric-only allow-list ["ES256","RS256"] (no HS256/none), audience="authenticated", expiry checked, sub required, JWKS kid-rotation handled (auth.py:23-35). HS256-confusion rejection is unit-tested (test_auth.py:61-69).
  • No SQL injection surface. Every query parameterized (db.py:42-56); vector_literal emits only numeric repr(float(x)) and rejects non-finite (db.py:22-25); ids bound as $n::uuid. No interpolated SQL.
  • Tenant isolation enforced server-side on every embedder path (owner filters with verified sub).
  • Storage paths owner-prefixed from the verified uid (storage.py:16-19); kind whitelisted (storage.py:17) — no path traversal.
  • Secrets hygiene: server/.env is git-ignored and untracked (.gitignore:10); no service-role/JWT secret in the iOS client (grep-confirmed).
